# Notes

## Reasons for studying programming language concepts
Six reasons. In the exam you may get a **scenario** (a junior programmer, a manager, a lecturer…) and must give the reason(s) that fit **that person** — not just any reason.

1. **Increased ability to express ideas** — you can't express what you can't describe; a language limits the structures you think in. Even if your language is dictated, knowing a feature lets you **simulate** it.
   *Fits:* a programmer stuck in one language who needs a construct it lacks.
2. **Improved background for choosing appropriate languages** — programmers often only know languages from in-house training or old formal training. Knowing concepts allows **informed choices**; a directly supported feature beats a simulated one.
   *Fits:* a **manager / team lead / architect** choosing a language for a new project.
3. **Increased ability to learn new languages** — computing is young; languages and usage keep changing. Concept knowledge **reduces learning time** and helps you read language documentation/literature.
   *Fits:* a **junior programmer** joining a company using an unfamiliar language; anyone facing a new language.
4. **Better understanding of the significance of implementation** — why languages work the way they do → use them as intended, understand **low-level bugs**, understand **efficiency trade-offs**.
   *Fits:* someone debugging a strange bug or optimising performance (e.g. recursion vs iteration cost).
5. **Better use of languages that are already known** — modern languages are large; most programmers use a subset. Knowing about features lets you **exploit** them.
   *Fits:* an experienced programmer in one big language (C++, Java).
6. **Overall advancement of computing** — language popularity is often not well founded (ALGOL 60 was better than Fortran but lost). If decision-makers understood the issues, **better languages would dominate**.
   *Fits:* a **lecturer**, a standards committee, people who influence which languages are adopted.

## Language evaluation criteria
- **Readability** — how easily programs can be **read and understood**.
- **Writability** — how easily the language can be used to **create** programs (for the chosen domain).
- **Reliability** — whether programs perform to their **specifications under all conditions**.
- **Cost** — the **ultimate total cost** of using the language.

## Readability in detail
**Overall simplicity**

- A **manageable** set of features and constructs.
- Minimal **feature multiplicity** (several ways to do one thing, e.g. `count++`, `++count`, `count += 1`, `count = count + 1`).
- Minimal **operator overloading**.
- Too much simplicity also hurts (e.g. assembly: simple, but programs are long and unreadable).

**Orthogonality** (will definitely be tested)

- A **relatively small set of primitive constructs** can be **combined in a relatively small number of ways**, and — most importantly — **every possible combination is legal**.
- A small set of constructs alone is **not** enough.
- An orthogonal feature is **context independent**. A lack of orthogonality shows up as **exceptions to the rules** ("you can do X, except when…").
- Too much orthogonality also hurts readability — **ALGOL 68** made so many combinations legal that programs became complex.

> Examples of *non*-orthogonality: in C, arrays can't be returned from functions but structs can; C parameters are passed by value except arrays (by reference); in Java only objects (not primitives) can be put in collections; Java has rectangular syntax but only jagged arrays.

**Data types** — adequate predefined types and structures. Missing types must be simulated (e.g. `int flag = 1` instead of a Boolean `true` — less readable).

**Syntax considerations**

- **Identifier forms** — naming restrictions (e.g. Fortran I's 6 characters) hurt readability.
- **Special words** — sensible, meaningful special words; how **compound statements** are closed (`end if` / `end loop` vs `}` everywhere).
- **Form and meaning** — self-descriptive constructs; avoid constructs that **look the same but mean different things** depending on context (e.g. C's `static`).

## Writability, reliability and cost
**Writability**

- **Simplicity and orthogonality** — few constructs, few primitives, a small set of combination rules.
- **Support for abstraction** — define and use complex structures/operations while ignoring details. **Process abstraction** (subprograms) and **data abstraction** (classes, pointers & dynamic memory).
- **Expressivity** — relatively convenient ways of specifying operations: strength and number of operators and predefined functions (e.g. `count++`, `for` vs `while`).

**Reliability**

- **Type checking** — testing for type errors; **compile-time is preferable** to run-time checking (cheaper to fix).
- **Exception handling** — intercept run-time errors and take corrective action.
- **Aliasing** — two or more names for the same memory cell; generally **dangerous**.
- **Readability and writability** — a language without "natural" ways to express an algorithm forces "unnatural" approaches → less reliable.

**Cost** — training programmers; writing programs (closeness to the application area); compiling; executing; the language implementation system (free compilers help adoption); **poor reliability = high cost**; **maintenance** (often the largest cost, driven by readability).

> In a modern context, the cost of executing and compiling has dropped (fast hardware); costs related to people — **training, writing, maintenance, and reliability failures** — matter most.

**Other criteria:** **portability** (moving programs between implementations), **generality** (applicable to many domains), **well-definedness** (completeness and precision of the official definition).

## Design trade-offs
- **Reliability vs cost of execution** — Java checks every array index: more reliable, slower.
- **Readability vs writability** — APL: many powerful (non-standard symbol) operators, very compact code, very poor readability.
- **Writability (flexibility) vs reliability** — C++ pointers: powerful and flexible, but unreliable.

## Programming domains
| Domain | Needs | Language |
|---|---|---|
| Scientific | lots of floating point and arrays | Fortran |
| Business | reports, decimal numbers, characters | COBOL |
| Artificial intelligence | symbols, linked lists | LISP |
| Systems programming | efficiency (used continuously) | C |
| Web | eclectic: markup, scripting, general purpose | HTML, PHP, Java |

## Influences on language design
**Computer architecture — the von Neumann architecture.** Data and programs stored in memory; memory separate from the CPU; instructions and data are **piped** from memory to the CPU. This is the basis of **imperative** languages:

- variables model **memory cells**,
- assignment statements model **piping**,
- **iteration** is efficient (instructions in adjacent cells), **recursion is discouraged**.

**Programming methodologies**

| Period | Focus | Result |
|---|---|---|
| 1950s – early 1960s | Simple applications; **machine efficiency** | Fortran-style languages |
| Late 1960s | **People efficiency**: readability, better control structures | Structured programming, top-down design, step-wise refinement |
| Late 1970s | **Process-oriented → data-oriented** | **Data abstraction** (SIMULA 67 was the first to support it) |
| Mid 1980s | Object-oriented programming | Data abstraction + inheritance + polymorphism |

## Language categories
- **Imperative** — variables, assignment, iteration. Includes OO languages, scripting languages and visual languages (C, Java, Perl, JavaScript, Visual BASIC .NET, C++).
- **Functional** — computation by **applying functions to parameters** (LISP, Scheme, ML, F#).
- **Logic** — **rule-based**, rules in no particular order (Prolog).
- **Markup/programming hybrid** — markup extended with some programming (JSTL, XSLT).

## Implementation methods
<!-- diagram:impl -->

- **Compilation** — translate the whole program to machine language: **slow translation, fast execution**. Large commercial applications.
- **Pure interpretation** — no translation; an interpreter runs the source. Easier to implement and **run-time errors can be shown immediately (in source terms)**, but **10–100× slower** (statements are decoded every time they run) and often **more space** (source and symbol table present at run time). Rare for traditional languages; common for **web scripting** (JavaScript, PHP).
- **Hybrid** — translate to an **intermediate language** that's easy to interpret (faster than pure interpretation). **Java**: byte code + byte code interpreter + run-time system = the **JVM** → portability. **Perl** is partially compiled to detect errors first.
- **Just-in-Time (JIT)** — a hybrid that translates to intermediate code, then **compiles each subprogram to machine code the first time it is called** and keeps it. "Delayed compilers". Used for Java and the .NET languages.

# Brief
**6 reasons** to study concepts: express ideas · choose languages · learn new languages · understand implementation · use known languages better · advance computing. **Match the reason to the person in the scenario.**

**4 criteria**: readability, writability, reliability, cost (+ portability, generality, well-definedness).

**Readability**: simplicity (few features, little multiplicity, little overloading), **orthogonality** (small set of primitives, small number of combining rules, *every combination legal*, context independent; too much = ALGOL 68), data types, syntax (identifiers, special words, form & meaning).

**Writability**: simplicity/orthogonality, abstraction (process & data), expressivity.
**Reliability**: type checking (compile-time best), exception handling, aliasing (bad), readability/writability.
**Cost**: training, writing, compiling, executing, implementation system, reliability, maintenance.

**Trade-offs**: Java index checks (reliability vs execution cost), APL (writability vs readability), C++ pointers (flexibility vs reliability).

**Domains**: scientific–Fortran, business–COBOL, AI–LISP, systems–C, web–mix.
**Influences**: von Neumann (variables = cells, assignment = piping, iteration good) and methodologies (machine efficiency → people efficiency → data-oriented → OOP).
**Categories**: imperative, functional, logic, markup hybrid.
**Implementation**: compilation (fast run), pure interpretation (slow, good errors, web scripts), hybrid (byte code, Java/Perl), JIT (compile on first call, Java/.NET).

# Traps
- Orthogonality needs **every combination to be legal** — a small set of constructs is not enough.
- Too much orthogonality hurts readability (ALGOL 68); too much simplicity hurts too.
- For scenario questions the reason must fit the person: manager → choosing languages; junior → learning new languages; lecturer/decision-makers → advancement of computing.
- Compile-time type checking is preferable to run-time checking.
- Interpretation gives better (source-level) error messages but is slower and uses more space.
- In the von Neumann model **recursion** is discouraged, **iteration** efficient.
- In a modern context people costs (writing, maintaining, reliability) outweigh compile/execute costs.
