# Notes

## Names
Imperative languages abstract the von Neumann machine: **variables abstract memory cells** and are characterised by attributes. Designing types (Ch 6) first needs names, bindings and scopes.

**Design issues for names (identifiers):** what forms can names take? Are special words reserved words or keywords?

**Length** — too short → not connotative.

| Language | Name length |
|---|---|
| Fortran I / 95 / 2003 | 6 / 31 / 63 |
| C99 | no limit, first 63 significant (external names: 31) |
| C++ | no limit (implementations often impose one) |
| C#, Ada, Java | no limit, all significant |

**Special characters** — PHP: all variable names start with `$`. Perl: the first character gives the type (`$` scalar, `@` array, `%` hash). Ruby: `@` instance variables, `@@` class variables.

**Case sensitivity** (C-based languages are case sensitive):

- **Readability** suffers — names that look alike are different (`myname` vs `myName`).
- **Writability** suffers — you must remember the exact case of predefined mixed-case names (`IndexOutOfBoundsException`).

**Special words** name actions and separate parts of statements (aid readability).

- **Reserved word** — can never be a user-defined name (`int` is always the type). Problem: too many → name collisions (**COBOL has ~300**).
- **Keyword** — special only in certain contexts. Fortran: `Real VarName` (keyword: type) vs `Real = 3.4` (variable named Real) — confusing for readability.

## Variables and their six attributes
A variable = an abstraction of a memory cell, characterised by **name, address, value, type, lifetime and scope**.

- **Name** — not all variables have one (heap-dynamic variables are nameless).
- **Address** — the memory address it's associated with; may differ at different times (e.g. a local in different calls). **Aliases** = two or more names for the same location — created via **pointers, references and unions** — bad for readability (the reader must remember them all) and reliability.
- **Value** — contents of the **abstract memory cell** (the physical cell(s) for the variable, e.g. a 4-byte float = 1 abstract cell).
- **Type** — determines the range of values (and precision for floats), the set of operations, and how values are stored.

## Binding and binding times
A **binding** is an association — between an attribute and an entity (variable ↔ type/value) or an operation and a symbol (`*` ↔ multiplication). **Binding time** = when it happens:

| Binding time | Example |
|---|---|
| Language design time | operator symbols to operations (`*` = multiply) |
| Language implementation time | floating-point type to a representation |
| Compile time | a C/Java variable to its type |
| Load time | a C/C++ `static` local variable to a memory cell |
| Run time | a non-static local variable to a memory cell |

- **Static binding** — occurs **before run time** and **remains unchanged** during execution.
- **Dynamic binding** — occurs **during execution** or **can change** during execution.

## Type binding
**Static type binding**

- **Explicit declaration** — a statement declares the type: `int myVar;`
- **Implicit declaration** — a default mechanism (first appearance or naming conventions): BASIC, Perl, Ruby, JavaScript, PHP; Fortran has both. *Advantage:* writability (minor). *Disadvantage:* **reliability** — typos create new variables instead of errors. Less trouble in **Perl** because the sigil (`$ @ %`) makes the type explicit in every use.
- **Type inferencing** — type determined from context: C# `var value = 12;` (the initial value fixes the type). Also Visual BASIC 9+, ML, Haskell, F#. The type is still **static** — it can't change later.

**Dynamic type binding** — type is set by **assignment** and can change:

```javascript
list = [2, 4.33, 6, 8];
list = 17.3;
```

Used in JavaScript, Python, Ruby, PHP, C# (limited).

- *Advantage:* **flexibility** (variables usable for any type; generic program units).
- *Disadvantages:* **cost** (dynamic type checking and usually pure interpretation) and **type errors are hard to detect**.

> Type inferencing vs dynamic typing: inferencing fixes the type **once** at compile time from context; dynamic typing lets the type **change** at every assignment.

## Storage binding and lifetime
**Allocation** = take a cell from the pool of available memory (a storage binding). **Deallocation** = return it. **Lifetime** = the time a variable is bound to a particular memory cell.

<!-- diagram:lifetime -->

**Static** — bound before execution, same cell throughout (C/C++ `static`).

```c
int f() { static int sVar = 10; return ++sVar; }   /* remembers between calls */
```

- ✓ efficient (**direct addressing**), **history-sensitive** subprograms.
- ✗ no recursion, storage can't be shared.

**Stack-dynamic** — bound when the **declaration is elaborated** (its code executes); all other attributes (type) are static. Normal C/Java locals.

- ✓ allows **recursion**, conserves storage.
- ✗ allocation/deallocation overhead, **no history sensitivity**, slower **indirect** access.

**Explicit heap-dynamic** — allocated/deallocated by explicit programmer **directives** at run time; **nameless**, accessed only through pointers/references. C++ `new`/`delete`, all Java objects.

```cpp
int* p = new int(12);
```

- ✓ custom dynamic storage management (linked structures).
- ✗ unreliable (hard to use correctly), inefficient (heap management, indirection), hard to implement.

**Implicit heap-dynamic** — allocation/deallocation caused by **assignment** (implies **dynamic type binding**). All APL variables; strings and arrays in Perl, JavaScript, PHP.

- ✓ flexibility (generic code).
- ✗ inefficient (most attributes bound dynamically), loss of error detection.

## Scope: static vs dynamic
**Scope** = the range of statements over which a variable is **visible**. **Local** variables are declared in the unit; **non-local** are visible but declared elsewhere; **global** variables are a special category of non-local.

**Static (lexical) scope** — based on the **program text**. To find a name's declaration, search the local unit, then increasingly larger **enclosing scopes** (**static ancestors**; the nearest is the **static parent**), stopping at the first declaration. A closer variable with the same name **hides** the ancestor's.

Nested subprogram definitions (nested static scopes): Ada, JavaScript, Common LISP, Scheme, Fortran 2003, F#, Python.

**Dynamic scope** — based on the **calling sequence** (temporal, not spatial): search back through the chain of **active subprogram calls**.

<!-- diagram:scope -->

**Evaluation of static scope:** works well in many situations, but usually gives **too much access**; as programs evolve, locals tend to become global and subprograms tend to become global rather than nested.

**Evaluation of dynamic scope:**

- ✓ convenience — called subprograms see the caller's variables, so fewer parameters are needed.
- ✗ while a subprogram runs, **its variables are visible to every subprogram it calls** (no protection).
- ✗ **impossible to statically type check** non-local references (which variable is meant is only known at run time).
- ✗ programs are **harder to read** (you must know the call sequence).
- ✗ **slower** non-local access.

## Blocks, let, declaration order and globals
**Blocks** (from ALGOL 60) create static scopes inside program units:

```c
void sub() {
  int count;
  while (...) {
    int count;   /* hides the outer count — legal in C/C++ */
    count++;
  }
}
```

**Java and C# disallow** hiding in nested blocks (considered error-prone).

**let** in functional languages: first part binds names to values, second part uses them (Scheme `let` — see Ch 15).

**Declaration order**

- C99, C++, Java, C#: declarations may appear anywhere a statement can.
- C99, C++, Java: a local's scope is from its **declaration to the end of the block**.
- C#: a variable's scope is the **whole block**, but it can only be **used after** its declaration. So an inner `int x;` followed later by an outer `int x;` in the same enclosing block is **illegal in C#** (the outer x's scope covers the inner block too) but legal in C++/Java.
- C++, Java, C#: a `for` header variable's scope is limited to the loop.

**Global scope**

- C, C++, PHP, Python: a program can be a sequence of function definitions; globals are declared outside functions.
- **PHP:** a variable implicitly declared outside functions has scope from its declaration to the end of the program **but skips functions**. Inside a function, globals are only accessible via the `$GLOBALS` array or by declaring them `global`.
- **Python:** globals can be **referenced** in functions, but can only be **assigned** if declared `global` in the function.

## Scope vs lifetime, and referencing environments
Scope and lifetime are often related but are **different concepts**:

- A Java local: scope = its block; lifetime = while the method runs.
- A C `static` local: scope = **only the function** (static, textual); lifetime = **whole program execution**.

**Referencing environment** of a statement = the collection of **all names visible** in it.

- Static scope: the local variables + visible variables of **all enclosing scopes**.
- Dynamic scope: the local variables + visible variables of **all active subprograms** (started but not yet finished).

```
Main()  { def A, B;
  Sub1 { def B, C;  (2)  call Sub2; }
  Sub2 { def C, D;  (3) }
  (1)  call Sub1;
}
```

| Point | Static scoping | Dynamic scoping |
|---|---|---|
| (1) | A, B of Main | A, B of Main |
| (2) | B, C of Sub1; A of Main | B, C of Sub1; A of Main |
| (3) | C, D of Sub2; **A, B of Main** | C, D of Sub2; **B of Sub1**; A of Main |

## Named constants
A **named constant** is bound to a value **only once**; used to parameterise programs → better **readability and reliability** (change one definition, not every literal).

```cpp
const int SIZE = 10;
int arr[SIZE];
```

- **Static** binding of values (manifest constants): `const int SIZE = 10 + 5;`
- **Dynamic** binding: value computed at run time, e.g. from a variable.

C++, Java, Ada: any expression (so possibly dynamic). C#: `const` (bound at **compile** time) and `readonly` (bound **dynamically**).

# Brief
**Names**: length limits, special characters (PHP `$`, Perl `$@%`, Ruby `@ @@`), case sensitivity (hurts readability & writability), reserved words (never user names) vs keywords (special in context).

**6 attributes**: name, address, value, type, lifetime, scope. Aliases (pointers, references, unions) hurt readability.

**Binding times**: design (operators), implementation (FP representation), compile (C/Java types), load (C static), run (locals). Static = before run time & unchanging; dynamic = during run time or changeable.

**Type binding**: explicit, implicit (writable but unreliable; Perl sigils help), inferencing (C# `var` — still static), dynamic (JS/Python — flexible, costly, poor error detection).

**Lifetimes**: static (fast, history-sensitive, no recursion) · stack-dynamic (recursion, no history) · explicit heap-dynamic (`new`, nameless, unreliable) · implicit heap-dynamic (assignment, flexible, slow).

**Scope**: static = text, search enclosing scopes (too much access); dynamic = call chain (convenient, unsafe, unreadable, no static type checking, slow).
Blocks hide outer names (illegal in Java/C#). C#: scope = whole block. PHP/Python globals need `global` (Python only to assign).

**Referencing environment**: static → locals + enclosing scopes; dynamic → locals + all active subprograms.
**Named constants**: bound once, readability + reliability; C# `const` (compile time) vs `readonly` (dynamic).

# Traps
- C# type inferencing (`var x = 12`) is **static** type binding, not dynamic.
- Implicit heap-dynamic variables imply **dynamic type binding**.
- A C `static` local has **local scope** but **program-long lifetime** — scope ≠ lifetime.
- Static variables can't support recursion; stack-dynamic variables can't be history-sensitive.
- Dynamic scope: the referencing environment includes variables of **all active** subprograms, not just the caller.
- Java/C# disallow hiding a variable in a nested block; C/C++ allow it.
- In PHP a global is **not** visible in functions unless declared `global` or accessed via `$GLOBALS`; in Python it's readable but only assignable with `global`.
- Explicit heap-dynamic variables are nameless (accessed through pointers/references).

# Flashcards
Q: The six attributes of a variable?
A: Name, address, value, type, lifetime, scope.

Q: Reserved word vs keyword?
A: Reserved word can never be a user-defined name. Keyword is special only in certain contexts (e.g. Fortran Real).

Q: Example of load-time binding?
A: A C/C++ static local variable bound to a memory cell.

Q: Advantage and disadvantage of implicit declarations?
A: Advantage: writability. Disadvantage: reliability — typos aren't detected. Perl suffers less because sigils show the type.

Q: Static variables: pros and cons?
A: Pros: efficient direct addressing, history-sensitive subprograms. Cons: no recursion, storage can't be shared.

Q: Stack-dynamic variables: pros and cons?
A: Pros: recursion, conserves storage. Cons: allocation overhead, not history-sensitive, indirect addressing.

Q: Explicit heap-dynamic variables?
A: Allocated/deallocated by programmer directives (new/delete), nameless, accessed via pointers. Flexible but unreliable and inefficient.

Q: Implicit heap-dynamic variables?
A: Allocated by assignment (APL, JS arrays/strings). Flexible but inefficient and poor error detection; implies dynamic typing.

Q: Static vs dynamic scope?
A: Static: based on program text (enclosing declarations). Dynamic: based on the calling sequence of active subprograms.

Q: Disadvantages of dynamic scope?
A: Local variables visible to called subprograms, no static type checking of non-locals, poor readability, slower non-local access.

Q: Referencing environment under dynamic scoping?
A: Local variables plus visible variables in all active subprograms.

Q: Why is a later outer declaration illegal in C# when an inner block declares the same name?
A: In C# a variable's scope is the whole block it's declared in, so the outer variable's scope overlaps the inner one.

Q: C# const vs readonly?
A: const values bound at compile time (static); readonly values bound dynamically.

Q: How can a PHP function access a global variable?
A: Via the $GLOBALS array or by declaring it global in the function.
