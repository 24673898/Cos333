# Notes

## What a data type is
A data type defines a **collection of values**, **how they're stored**, and a set of **predefined operations**. Design issues for every type: which operations are defined, and how types are specified.

> Not examinable: implementation sections (6.3.5, 6.5.9, 6.6.2, 6.7.4, 6.10.5, 6.11.7), 6.4 (user-defined ordinal types), 6.5.4, 6.12, 6.16. For 6.15 (type equivalence) only the slide content.

## Primitive data types
Primitive types are **not defined in terms of other types**; some just reflect the hardware, others need a little software support.

- **Integer** — up to 8 sizes (Java: `byte short int long`); some languages add unsigned integers.
- **Floating point** — approximations of reals; scientific languages have at least two (`float`, `double`). IEEE 754 is common. **Precision** = accuracy of the fractional part; **range** = min/max values.
- **Complex** — pair of floats (real + imaginary): C99, Fortran, Python (`7 + 3j`).
- **Decimal** — fixed number of decimal digits stored in **BCD**: essential to COBOL, available in C#. ✓ **accuracy** (money). ✗ wastes memory, limited range.
- **Boolean** — two values. Could be bits, but usually stored as bytes (addressing). ✓ **readability** (vs using ints).
- **Character** — numeric codes: ASCII; Unicode UCS-2 (16-bit, most natural languages); UCS-4/UTF-32 (Fortran 2003+, Java, C#).

## Character strings
Design issues: is a string a **primitive type** or a special kind of **array**? Is its length **static or dynamic**?

| Language | Strings |
|---|---|
| C, C++ | not primitive — `char` arrays + a function library |
| Fortran, Python | primitive type with assignment and operations |
| Java | primitive via the `String` class; `StringBuffer` behaves like a char array |

**Length options**

- **Static length** — fixed when created: COBOL, Java `String`.
- **Limited dynamic length** — up to a maximum; a special character marks the end, length isn't stored explicitly: C, C++.
- **Dynamic length** — no maximum: Perl, JavaScript (most flexible, most overhead).

## Arrays: indexing and binding categories
An array is a **homogeneous** aggregate; an element is identified by its **position relative to the first**.

**Design issues:** legal subscript types; range checking; when subscript ranges are bound; when allocation happens; max subscripts; ragged and/or rectangular; initialisation; slices.

**Index syntax:** most languages use `[ ]`; Fortran, PL/I and **Ada use `( )`** — Ada does it deliberately for **uniformity**: array references and function calls are both **mappings**.

**Range checking:** C, C++, Perl, Fortran — **no** checking (faster, but unreliable). Java, ML, C# — **checked** (reliable, slower).

| Category | Subscript range | Storage | Example | Advantage |
|---|---|---|---|---|
| **Static** | static | static (before run time) | C `static` arrays | efficiency (no dynamic allocation) |
| **Fixed stack-dynamic** | static | allocated at declaration elaboration (stack) | C local arrays | space efficiency (storage reused) |
| **Stack-dynamic** | dynamic, then fixed | dynamic, then fixed (stack) | ALGOL 60 / Ada | flexibility — size known only when used |
| **Fixed heap-dynamic** | dynamic, then fixed | heap, on request | C++ `new int[size]`, **all Java arrays** | flexibility |
| **Heap-dynamic** | dynamic, can change any time | heap | Perl, JS, Python, Ruby; C# `ArrayList` | grows/shrinks as needed (✗ allocation cost) |

C/C++: `static` arrays are static, otherwise fixed stack-dynamic; plus fixed heap-dynamic via `new`/`malloc`. C# similar, plus heap-dynamic `ArrayList`.

**Heterogeneous arrays** (elements of different types) — Perl, Python, JavaScript, Ruby — are really homogeneous arrays of a **generic value type** (e.g. `Object`).

## Array operations, rectangular vs jagged, slices, associative arrays
**Operations**

- **APL** — very powerful operations on vectors, matrices and scalars (e.g. reverse columns).
- **Python, Java** — array assignment only changes a **reference**; Java `clone()` copies. Python has catenation and membership.
- **Fortran** — **elemental** operations between element pairs: `C = A + B` adds element by element. Justified by Fortran's **scientific domain** (vector/matrix maths).

**Rectangular vs jagged**

- **Rectangular** — every row has the same number of elements (and every column): Fortran, Ada.
- **Jagged** — rows of varying length, implemented as **arrays of arrays**: C, C++, Java.
- **C# and F# support both.**

> A jagged array is just the orthogonal combination "array whose element type is an array"; a rectangular array is a separate special construct. So rectangular arrays are the **less orthogonal** feature. Not every jagged array can be turned into a rectangular one (rows have different lengths).

**Slices** — a substructure of an array, a **referencing mechanism** that retrieves part of an array as a unit (e.g. Fortran 95 rows/columns of a matrix).

**Associative arrays** — **unordered** collections indexed by **keys** (user keys must be stored). Built in to Perl (hashes), Python, Ruby, Lua (tables), Swift. Design issues: the form of element references; static or dynamic size.

## Records and tuples
A **record** is a possibly **heterogeneous** aggregate whose elements (**fields**) are identified by **name**. Design issues: syntax of field references; are **elliptical references** allowed?

COBOL uses **level numbers** for nested records:

```
01 EMPLOYEE-RECORD.
   02 EMPLOYEE-NAME.
      05 FIRST   PICTURE IS X(20).
      05 MIDDLE  PICTURE IS X(10).
      05 LAST    PICTURE IS X(20).
   02 HOURLY-RATE PICTURE IS 99V99.
```

Other languages nest record **types** inside records (orthogonal, e.g. Ada).

- **Fully qualified reference** — includes every record name: `MIDDLE OF EMPLOYEE-NAME OF EMPLOYEE-RECORD` (COBOL) or `Employee_Record.Employee_Name.Middle` (dot notation).
- **Elliptical reference** — leave out record names if unambiguous: `FIRST`, `FIRST OF EMPLOYEE-NAME`, `FIRST OF EMPLOYEE-RECORD` are all equivalent in COBOL (writable, less readable).

**Tuples** — like records but elements are **unnamed** (referenced by position). Python, ML, F#; let functions **return multiple values**. Python tuples are **immutable**: `myTuple = (3, 5.8, 'apple')`, `myTuple[0]` → `3`.

## Lists
- **LISP/Scheme** lists — linked, **immutable** (Ch 15).
- **Python lists** — also serve as heterogeneous arrays; **mutable**; any element types; zero-based subscripts; `del myList[1]` deletes.

**List comprehensions** (from set notation):

```python
list = [x ** 2 for x in range(12) if x % 3 == 0]   # [0, 9, 36, 81]
```

`range(12)` gives 0–11; keep those divisible by 3 (0, 3, 6, 9) and square them. (The slide also lists 12 → 144, but `range(12)` stops at 11 — if the exam asks, go with real Python behaviour and mention the range.) They make list operations more **writable** (compact) — at some cost to readability for non-experts.

## Unions — free vs discriminated
A **union** can store values of **different types at different times**, but holds **one value at a time** (the alternatives share memory). Design issues: should type checking be required? Should unions be embedded in records?

**Free unions** — Fortran, C, C++: **no type checking**; the programmer must track what's stored.

```c
union flexType { int intEl; float floatEl; };
union flexType u1;
u1.floatEl = 22.8;
int y = u1.intEl;   /* legal, but reinterprets the float's bits → garbage */
```

**Discriminated unions** — ML, Haskell, F#: each union has a **type indicator** — a **discriminant** or **tag** — that the language uses to **check** accesses and detect errors.

Free unions are a reason C/C++ are **not strongly typed**.

## Pointers and references
A **pointer** variable holds memory addresses (or `nil`). Two uses: **indirect addressing** (refer to a variable via another name) and **dynamic memory management** (access heap-dynamic variables).

**Design issues:** scope and lifetime of the pointer; lifetime of the heap-dynamic variable; restrictions on what can be pointed to; used for dynamic storage, indirect addressing, or both; support pointers, references, or both?

**Operations**

- **Assignment** — set a pointer to an address (`int *p = &val;`).
- **Dereferencing** — get the value at the address; explicit (`j = *ptr;` in C++) or **implicit** (automatic).

**Problems**

- **Dangling pointer** — points to a heap-dynamic variable that has been **deallocated** (dangerous: the memory may be reused).
- **Lost heap-dynamic variable (garbage)** — allocated but no longer accessible, e.g. `p1` re-pointed to new memory without freeing the old → **memory leakage**.

**C and C++ pointers** — extremely flexible: point anywhere regardless of allocation; explicit `*` and `&`; pointer arithmetic; `void*` can point to any type but can't be dereferenced without a cast (weakens type checking). Heap: C++ `new`/`delete[]`; C `malloc`/`free`.

**References**

- **C++ references** (`int &ref = v;`) — constant pointers, implicitly dereferenced; used mostly for **formal parameters** (pass-by-reference efficiency with value-like syntax). Safer: no address arithmetic.
- **Java** — references **replace pointers entirely**, and can refer only to **objects** (not primitives) → more reliable, less flexible/writable.
- **C#** — Java-style references **plus** C++ pointers, but pointers only in methods marked **`unsafe`** → flexibility when needed while keeping the default safe.

> Writability ranking for pointer/reference support: **C++** (pointers + references) is the most flexible/writable; Java the most restricted (and most reliable).

## Type checking, strong typing and type equivalence
Generalise: subprogram calls and assignments are operators with operands.

- **Type checking** ensures an operator's operands are of **compatible types** — either legal for the operator, or allowed to be implicitly converted (**coercion**).
- **Type error** — an operator applied to an operand of an inappropriate type.
- If all type bindings are **static**, almost all checking can be **static**; with **dynamic** type binding checking must be **dynamic**.

**Strongly typed** language = **type errors are always detected**. Usually relative ("A is more strongly typed than B").

- **C and C++** are not: pre-C99 parameter checking can be avoided, **free unions** aren't checked, `void*`, many coercions.
- **Java and C#**: implicit type errors can't go undetected, but **explicit casts** can cause type errors at run time (`(Student) p` when `p` is a `Lecturer`) → more strongly typed than C/C++, but not perfectly.

**Coercion weakens typing:** if `a` and `b` are `int` and `d` is `float`, mistyping `a + d` for `a + b` isn't caught — `a` is silently converted. C++ has many coercions (less reliable); Java has about half its assignment coercions (more reliable).

**Type equivalence** (when two types are substitutable with no coercion):

- **Name type equivalence** — same type **name** only. Easy to implement but **restrictive** (e.g. call parameters must exactly match the definition's types).
- **Structure type equivalence** — identical **structure**. More **flexible**, but **harder to implement**.

# Brief
**Primitives**: integer, float (precision vs range), complex, decimal (BCD: accurate, wasteful), Boolean (readability), character (ASCII, Unicode).
**Strings**: C/C++ char arrays; Java `String`; length static (COBOL, Java String) / limited dynamic (C) / dynamic (Perl, JS).

**Array categories**: static · fixed stack-dynamic (C locals) · stack-dynamic · fixed heap-dynamic (all Java arrays, C++ `new`) · heap-dynamic (Perl/JS/Python/Ruby, C# ArrayList).
Range checking: Java/C#/ML yes; C/C++/Perl/Fortran no. Ada uses `( )` for uniformity with function calls.
Rectangular (Fortran, Ada) vs jagged = arrays of arrays (C, C++, Java); C# and F# have both. Fortran elemental ops fit the scientific domain.
Slices = referencing mechanism. Associative arrays = keyed, unordered (Perl hashes, Python dicts, Lua tables).

**Records**: named heterogeneous fields; COBOL level numbers; fully qualified vs elliptical references. **Tuples**: unnamed fields, immutable in Python. **Python lists** mutable; comprehensions = writability.
**Unions**: free (C/C++/Fortran — unchecked) vs **discriminated** (tag checked: ML, Haskell, F#).
**Pointers**: indirect addressing + heap management; dangling pointers & lost heap variables (leaks). C++ references safe for parameters; Java references only (objects); C# both (pointers only `unsafe`).
**Strong typing** = all type errors detected; C/C++ weak, Java/C# stronger. Coercion weakens typing.
**Type equivalence**: name (simple, restrictive) vs structure (flexible, hard to implement).

# Traps
- **All Java arrays are fixed heap-dynamic** (not stack-dynamic) — even local ones.
- Rectangular arrays are **less orthogonal** than jagged arrays (jagged = arrays of arrays, a free combination).
- Java supports only jagged arrays; **C# supports both** → C# is more flexible here.
- A free union lets you read a float's bits as an int — legal but garbage; a discriminated union's tag prevents that.
- Dangling pointer = memory freed but pointer remains; lost heap-dynamic variable = memory remains but no pointer.
- Java/C# aren't perfectly strongly typed — explicit casts can still fail at run time.
- Coercion reduces the compiler's ability to detect type errors.
- C# pointers exist only in `unsafe` methods.

# Flashcards
Q: Decimal type: storage, advantage, disadvantages?
A: Stored in BCD (fixed decimal digits). Accurate (money); wastes memory and has limited range.

Q: Three string length options with examples?
A: Static (COBOL, Java String), limited dynamic (C/C++ — end marker), dynamic (Perl, JavaScript).

Q: Why does Ada use parentheses for array indexing?
A: Uniformity — array references and function calls are both mappings.

Q: What array category are Java arrays?
A: Fixed heap-dynamic.

Q: Rectangular vs jagged arrays?
A: Rectangular: all rows/columns same length (Fortran, Ada). Jagged: rows vary; arrays of arrays (C, C++, Java). C# and F# support both.

Q: What is a slice?
A: A substructure of an array — a referencing mechanism that retrieves part of an array as a unit.

Q: Fully qualified vs elliptical record references?
A: Fully qualified includes all enclosing record names; elliptical omits them when unambiguous (COBOL).

Q: Tuple vs record?
A: Tuple elements are unnamed (positional); record fields are named. Python tuples are immutable.

Q: Free vs discriminated union?
A: Free: no type checking (C, C++, Fortran). Discriminated: a tag/discriminant is checked on access (ML, Haskell, F#).

Q: Dangling pointer vs lost heap-dynamic variable?
A: Dangling: pointer to deallocated memory. Lost: allocated memory with no pointer to it (garbage → memory leak).

Q: Why are C and C++ not strongly typed?
A: Unchecked (free) unions, parameter checking can be avoided pre-C99, void pointers, many coercions.

Q: Name vs structure type equivalence?
A: Name: same type name required — easy but restrictive. Structure: identical structure — flexible but harder to implement.

Q: How do C# references and pointers differ from Java's?
A: C# has Java-like references plus C++-style pointers, but pointers only in unsafe subprograms; Java has references only.

Q: Evaluate [x ** 2 for x in range(12) if x % 3 == 0].
A: [0, 9, 36, 81].
