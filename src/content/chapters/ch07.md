# Notes

## Arithmetic expressions and their design issues
Expressions are the fundamental way to specify computation; to understand them you need the **order of operator and operand evaluation**. Assignment is the essence of imperative languages.

An arithmetic expression = **operators**, **operands**, **parentheses**, **function calls**. Operators are **unary** (1 operand), **binary** (2) or **ternary** (3).

**Design issues**

1. Operator **precedence** rules?
2. Operator **associativity** rules?
3. Order of **operand evaluation**?
4. Are operand evaluation **side effects** restricted?
5. Is **user-defined operator overloading** allowed?
6. What **type mixing** is allowed?

## Precedence and associativity
**Precedence** decides the order in which **adjacent operators of different precedence levels** are evaluated. Typical levels (high → low): parentheses → unary operators → `**`/`^` (exponent: Fortran, Ruby, Ada, Visual Basic) → `* /` → `+ -`.

**Associativity** decides the order for **adjacent operators of the same level**: usually **left to right**, except `**` (**right to left**); some unary operators are right to left.

**APL** has **one precedence level** and **all operators associate right to left** — simple and uniform (orthogonal), but unusual for readers.

Parentheses override both rules.

**Ruby:** most operators (arithmetic, relational, assignment, array indexing, shifts, bitwise) are **methods** → **all can be overridden** by the programmer. Flexible/orthogonal and writable, but can hurt readability and reliability (an operator may not mean what you expect).

**Scheme/Common LISP:** all arithmetic and logic operations are **explicitly called subprograms** — `a + b * c` is `(+ a (* b c))`. The nesting makes order explicit, so there are **no precedence or associativity rules** to remember. Because Scheme is **dynamically typed**, operator overloading doesn't make sense (there are no static types to choose between).

## Conditional expressions and operand evaluation order
**Conditional expression** (C-based languages):

```c
average = (count == 0) ? 0 : sum / count;
```

Equivalent to an `if` that assigns in both branches. More **writable**/compact; can be less readable when nested.

**Operand evaluation order**

1. **Variables** — fetch the value from memory.
2. **Constants** — sometimes a memory fetch, sometimes part of the instruction.
3. **Parenthesised expressions** — evaluate everything inside first.
4. **Function calls with side effects** — the interesting case: the order changes the result (see Ch 15: `b = a + fun(&a)`). Solutions: ban side effects or fix the evaluation order.

## Overloaded operators
**Operator overloading** = using an operator for more than one purpose.

- Common and safe: `+` for `int` and `float` addition.
- Problematic: C/C++ **`&`** — binary = bitwise AND; unary = address-of (and reference declaration). Problems: **loss of readability** and **loss of compiler error detection** — forget the first operand of `x & y` and `&y` is silently accepted as address-of. Same issue with `*` (multiply vs dereference).

**User-defined overloading** (C++, C#, F#, also Python/Ruby):

- ✓ can **aid readability** when used sensibly (`a + b` instead of `a.add(b)`).
- ✗ users can define **nonsensical** operations; to understand an operator the reader must know the **operand types**; and different sensible meanings exist (adding lists: concatenate or add pairwise?).

## Type conversions and mixed-mode expressions
- **Narrowing conversion** — to a type that can't hold all values of the original (float → int). **Not always safe** — magnitude may be lost.
- **Widening conversion** — to a type that holds at least approximations of all the original's values (int → float). **Generally safe** (magnitude kept) but may lose **accuracy**.

A **mixed-mode expression** has operands of different types (`int a + float b`). **Coercion** = implicit (automatic) conversion so the operation can happen. Coercion **decreases the compiler's type-error detection** (a typo using the wrong variable is silently converted).

- Most languages coerce numeric types in expressions using **widening** conversions (safer).
- **ML and F#** do **no coercions** in expressions → mixed-mode arithmetic must use explicit conversions: **more reliable**, **less writable**. (So C++ mixed-mode is *more writable* than F#; F#'s is *more reliable*.)

**Explicit conversion (casting)** — programmer-specified, narrowing or widening. C: `(int) angle`; F#: `float(sum)` (function-call syntax).

**Errors in expressions:** type checking and coercion; inherent arithmetic limits (**division by zero**); computer arithmetic limits (**overflow**, underflow). Some may be ignored; others need exception handling.

## Relational and Boolean expressions
Relational expressions yield Booleans.

- **JavaScript, PHP:** `==` / `!=` **coerce** operands (`"7" == 7` is true); `===` / `!==` don't (`"7" === 7` is false).
- **Ruby:** `==` numeric equality with coercion; `eql?` without coercion.

**C89 has no Boolean type** — it uses `int`: non-zero = true, 0 = false; Boolean expressions evaluate to 1 or 0. Odd result: `a < b < c` is **legal** but means `(a < b)` → 0 or 1, then `0/1 < c`. This is **less reliable** (no type checking of Booleans; nonsense accepted) and less readable than Java's `boolean`.

## Short-circuit evaluation
The result is determined **without evaluating all operands/operators**. `(13 * a) * (b / 13 - 1)` — if `a` is 0 the second factor is irrelevant.

Why it matters — without short-circuit `&&`, this reads past the end of the array:

```c
index = 0;
while ((index < length) && (list[index] != value))
    index++;
```

- C, C++, Java: `&&` and `||` short-circuit; bitwise `&` and `|` don't.
- Ruby, Perl, ML, F#, Python: **all** logic operators short-circuit.

**Problem with side effects:**

```c
(a > b) || (b++ / 3)
```

If `a > b`, the right side is skipped, so **`b++` (the side effect) doesn't happen**. Code that relies on the side effect happening every time breaks.

> 2025 exam pattern: `while ((total <= 100) or ((input = read()) != EOF))` — with short-circuit `or`, whenever `total <= 100` is true the read is skipped, so `input` never changes. The problem is that **with short-circuit evaluation a side effect will not occur**.

## Assignment statements
General syntax: `<target> <assign_operator> <expression>`. `=` in Fortran, BASIC and C-based languages; `:=` in the ALGOLs, Pascal, Ada.

If `=` is also the equality operator, assignment and comparison are **ambiguous**. C-based languages use `==` for equality; ALGOL's `:=` avoids the issue.

**Conditional targets** (Perl):

```perl
($flag ? $total : $subtotal) = 0;
```

Equivalent to an `if/else` assigning 0 to one of two variables. More writable, **less readable**.

**Compound assignment operators** (ALGOL 68 → C): `a += b` ≡ `a = a + b`. A shorthand → **writability**; not essential, and not about orthogonality.

**Unary assignment operators** (C-based): `sum = ++count` (increment, then assign), `sum = count++` (assign, then increment). Postfix `++`/`--` associate left to right; prefix `++`/`--` and unary `+`/`-` right to left: `-++count` ≡ `-(++count)`.

**Assignment as an expression** (C-based languages, Perl, JavaScript): an assignment **produces a value** (the value assigned), so it can be an **operand**:

```c
while ((ch = getchar()) != EOF) { ... }
```

Problems: **less error detection** — `if (x = y)` is legal when you meant `==`; and assignment inside an expression is a **side effect** (it changes an operand).

**Multiple assignment** (Perl, Ruby, Lua): `($first, $second, $third) = (20, 30, 40);` and an easy swap `($first, $second) = ($second, $first);` → writability.

**Assignment in functional languages:** identifiers are just **names for values**. ML `val fruit = apples + oranges;` — a later `val fruit = …` creates a **new name that hides** the old one (not an error, not reassignment). F#'s `let` is similar but also **creates a new scope**.

## Mixed-mode assignment
The target and the expression have different types.

- **Fortran, C, C++, Perl:** coercion rules allow assigning **any numeric value to any numeric variable** — including narrowing (e.g. float into int silently truncates) → errors go undetected.
- **Java and C#:** only **widening** assignment coercions → safer: no silent loss of magnitude.

> Remember from Ch 15: side effects and **referential transparency** are examinable here too.

# Brief
**Design issues**: precedence, associativity, operand order, side effects, overloading, type mixing.
**Precedence** = different levels; **associativity** = same level (left→right; `**` right→left). APL: one level, right→left. Ruby operators are overridable methods. Scheme prefix calls make precedence irrelevant; dynamic typing makes overloading meaningless.

**Conditional expression** `c ? x : y`. **Operand order** matters only with side effects.
**Overloading**: `&` in C/C++ (readability + error detection lost); user-defined (C++, C#, F#): readable if sensible, abusable.
**Conversions**: narrowing unsafe, widening safe (may lose accuracy). **Coercion** reduces error detection. ML/F#: no coercion (reliable, less writable). Casting = explicit.

**Relational**: JS/PHP `==` coerces, `===` doesn't; Ruby `eql?`. C89 ints as Booleans → `a < b < c` legal but wrong (less reliable).
**Short-circuit**: `&&`/`||` in C-family; all logic ops in Ruby/Perl/Python/ML/F#. Danger: skipped side effects.
**Assignment**: `=` vs `:=`; conditional targets (Perl); compound `+=` (writability); `++`/`--`; assignment as expression (`while ((ch = getchar()) != EOF)`, `if (x = y)` bug); multiple assignment (Perl/Ruby/Lua). ML `val` rebinding = new name hiding old.
**Mixed-mode assignment**: C/C++/Fortran/Perl any numeric → any numeric; Java/C# widening only (safer).

# Traps
- Associativity is about **equal** precedence; precedence is about **different** levels.
- `**` associates **right to left**.
- In ML, `val quantity = 6;` after `val quantity = 5;` creates a **second identifier that hides the first** — no error, no reassignment.
- `if ((var := readFromFile(...)) = "5")` shows a language that **supports assignment as an expression** — not a mixed-mode error.
- Compound assignment operators improve **writability** (they are not essential and don't affect orthogonality).
- C89 Booleans (ints) are **less reliable** than Java's `boolean`.
- With **short-circuit** evaluation, a side effect in the right operand may **not** happen.
- F# doesn't coerce in expressions → C++ mixed mode is more **writable**, F#'s more **reliable**.
- Conditional targets increase writability but **reduce readability**.

# Flashcards
Q: Precedence vs associativity?
A: Precedence orders adjacent operators of different levels; associativity orders adjacent operators of the same level.

Q: APL's precedence/associativity rules?
A: All operators have one precedence level and associate right to left.

Q: Why are precedence rules unnecessary in Scheme?
A: Operations are explicit prefix function applications; nesting makes the order explicit.

Q: Problems with overloading & in C/C++?
A: Loss of readability, and loss of error detection (omitting the left operand turns AND into address-of silently).

Q: Narrowing vs widening conversion?
A: Narrowing: target can't hold all source values (float→int, unsafe). Widening: target holds approximations of all values (int→float, safe but may lose accuracy).

Q: Why is coercion a reliability concern?
A: It reduces the compiler's ability to detect type errors — wrong-type operands are silently converted.

Q: JS == vs ===?
A: == coerces operands ("7" == 7 true); === does not ("7" === 7 false).

Q: What does a < b < c do in C?
A: Legal: (a < b) gives 0 or 1, which is then compared with c — not the mathematical meaning.

Q: Why must && be short-circuit in while ((i < len) && (list[i] != v))?
A: Otherwise list[i] is evaluated when i == len — out of bounds.

Q: Danger of short-circuit evaluation?
A: Side effects in the right operand (e.g. b++) won't occur when the left operand decides the result.

Q: What is a conditional target?
A: Perl: ($flag ? $total : $subtotal) = 0 — the conditional chooses which variable is assigned.

Q: Problems with assignment as an expression?
A: Reduced error detection (if (x = y) instead of ==) and side effects inside expressions.

Q: Mixed-mode assignment: C vs Java?
A: C/C++/Fortran/Perl allow any numeric→numeric coercion (incl. narrowing); Java/C# allow only widening — safer.

Q: What does a second ML val binding of the same name do?
A: Creates a new name that hides the previous one.
