# Notes

## Fundamentals and terminology (terminology is examined!)
Two fundamental abstraction facilities: **process abstraction** (subprograms — this chapter) and **data abstraction** (ADTs/OOP — Ch 12).

Characteristics of subprograms: **single entry point**; the **caller is suspended** while the called subprogram runs; control **always returns to the caller** when it ends. (Coroutines break these rules.)

| Term | Meaning |
|---|---|
| **Subprogram definition** | Interface (how it's used: name, parameter types…) + actions (the body) |
| **Subprogram header** | First part of the definition: name, kind of subprogram, formal parameters |
| **Subprogram call** | Explicit request to execute it |
| **Formal parameter** | Dummy variable in the header, used in the body |
| **Actual parameter** | Value/address used in the call |
| **Parameter profile (signature)** | Number, order and types of the parameters |
| **Protocol** | Parameter profile **+ return type** |
| **Subprogram declaration** | Protocol without a body (C/C++ **prototype**, usually in a header file) |

```c
void doSomething(int first, float second) { ... }   // header + formal parameters
doSomething(1, 23.7);                               // call + actual parameters
// profile: (int, float)   protocol: (int, float) → void
```

**Python:** `def` statements are **executable** — a function is defined only when its `def` runs, so an `if` can choose between two different definitions of `fun`. Implication: a function can't be called before its definition executes; flexible (writable), but harder to read/verify.

**Ruby:** methods defined inside a class are members; those defined outside are methods of class **`Object`** — they can be called without an object and look like C functions, but aren't.

## Actual/formal parameter correspondence
- **Positional** — first actual ↔ first formal, etc. Safe and effective; used by most languages. Drawback: with long parameter lists it's easy to mix up the order.
- **Keyword** — name the formal parameter in the call: `add(first = 10, second = 12, third = 3)`. Any order; avoids correspondence errors. Drawback: you must know the formal parameter **names**.

**Default values** (C++, Python, Ruby, Ada, PHP) — actuals can be omitted. In **C++ defaults must come last**, because parameters are positional — the compiler couldn't tell which ones were skipped. (Keyword parameters would allow defaults anywhere.)

**Variable number of parameters** (not the same as defaults — processed like a list):

- **C#** — formal parameter is an array preceded by **`params`**; all extras must be the **same type** (they're stored in a typed array):
  ```csharp
  public void DisplayList(params int[] list) { foreach (int next in list) ... }
  myObject.DisplayList(myList);              // pass an array
  myObject.DisplayList(2, 4, 3 * x - 1, 17); // or a list of values
  ```
- **Ruby** — extras arrive as elements of an `Array` (mixed types allowed — Ruby variables are typeless): `def tester(p1, p2, *p3)`.
- **Python** — similar to Ruby (a list/tuple of any types).

## Procedures, functions and design issues
- **Procedures** — parameterised computations that produce results by **modifying** non-local variables or formal parameters that pass data back; no return value.
- **Functions** — modelled on maths functions; produce results by **returning a value**; ideally **no side effects** (many languages allow them anyway).

**Design issues:** static or dynamic local allocation? nested definitions? which parameter-passing methods? are parameter types checked? referencing environment of a passed subprogram? are side effects allowed? which return types? how many return values? overloading? generics? closures?

**Local referencing environments:** locals are usually **stack-dynamic**. C/C++ locals are stack-dynamic by default but can be `static`. Java, Python and C# methods have **only** stack-dynamic locals.

## Parameter-passing methods
**Semantic models:** **in mode** (data to callee), **out mode** (data back to caller), **inout mode** (both).
**Conceptual models of transfer:** **physically copy a value**, or **transmit an access path** (address).

<!-- diagram:params -->

**Pass-by-value (in)** — the actual's value initialises the formal; usually by **copying**. ✗ extra storage and copy cost for large values. Could pass an access path instead but then the callee must be **write-protected** and access is indirect — not recommended.

**Pass-by-result (out)** — no value goes in; when the subprogram returns, the formal's value is **copied to the actual**.

```ada
procedure A_Test (A, B : in Integer; C : out Integer) is
begin C := A + B; end A_Test;
A_Test(5 + P, 48, Q);   -- Q is overwritten on return
```

Implemented by **copy** (an access path would make it reference semantics). Problems: extra storage and copy; **actual-parameter collisions** — `sub(p1, p1)`: p1's final value depends on the **order** the formals are copied back; and the time at which the actual's address is evaluated (call vs return) can matter.

**Pass-by-value-result (inout)** — copy in **and** copy out ("pass-by-copy"); formals have local storage. Has the disadvantages of both value and result.

**Pass-by-reference (inout)** — transmit an **access path** (pointer/reference); also called **pass-by-sharing**.

```cpp
void foo(int *p, int &r) { *p = 23 + r; r = 19 - *p; }
```

✓ efficient — no copying, no duplicate storage. ✗ slower formal access (indirect), unwanted **side effects**, and **aliases**: `fun(total, total)` makes `first` and `second` both refer to `total`.

**Pass-by-name (inout)** — **textual substitution**: every occurrence of the formal is replaced by the actual's text, bound to a value/address only **when used** (late binding). ALGOL 60; not used today.

```c
void foo(int a, int b) { a = 1; print(a, b); }
int val = 0; int arr[3] = {2, 8, 9};
foo(val, arr[val]);
// by value: prints 1 2
// by name : body becomes  val = 1; print(val, arr[val]);  → prints 1 8
```

## Parameter passing in real languages
| Language | Methods |
|---|---|
| C | pass-by-value; pass-by-reference simulated with **pointers** |
| C++ | value; reference via **pointers or reference** (`&`) parameters |
| Java | **all by value** — object *references* are passed by value (objects only *look* passed by reference) |
| Fortran 95+ | `in`, `out`, `inout` modes |
| C# | value by default; reference with **`ref`** on both formal and actual |
| Perl | actuals implicitly placed in **`@_`**, whose elements are **aliases** → **pass-by-reference** |
| Python, Ruby | **pass-by-assignment**: the actual (an object reference) is assigned to the formal → behaves like by-reference, except **immutable** objects (assigning a new value just rebinds the formal locally) |

## Type checking parameters, and arrays as parameters
Type checking parameters is **very important for reliability**.

- Fortran 77, original C, Perl, JavaScript, PHP — **no** checking (errors at run time / garbage).
- C89 offers a choice: old-style `double sin(x) double x; {...}` → no checking; prototype style `double sin(double x)` → checking **with coercion** (also C++).
- Pascal, Fortran 90, Java, Ada — **always** required.
- **Python, Ruby** — variables have no types (objects do: in `p = Person.new`, the object is a Person, `p` is typeless), so formal parameters **can't** be type checked.

**Multidimensional arrays as parameters**

- C/C++: the formal must give **all subscript sizes except the first** (`void fun(int matrix[][10])`) — inflexible. Workaround: pass a pointer plus the dimensions and use pointer arithmetic (flexible but unreadable/unsafe).
- Java/C#: arrays are objects that know their length (`length` / `Length`), so **no sizes** in the formal; multi-dimensional arrays are arrays of arrays.

## Subprograms as parameters and indirect calls
**Calling indirectly** — when the subprogram to call is only known at run time (e.g. event handling).

- **C/C++: function pointers** (include parameter and return types → can be type checked):
  ```cpp
  float (*ptr)(float, int) = myFunc;   ptr(1.8, 3);
  ```
- **C#: delegates** — objects holding method references; **multicast** delegates hold several and call them in sequence:
  ```csharp
  public delegate int Change(int x);
  Change myChangeFunction = new Change(m1);
  myChangeFunction += fun2;
  ```

**Subprogram names as parameters** — two issues: **are parameter types checked?** (C/C++ function pointers: yes; Fortran 95: yes; **Java doesn't allow** subprogram parameters) and **what is the referencing environment of the passed subprogram?** (only matters when nested subprograms are allowed and the passed subprogram uses a non-local variable).

<!-- diagram:binding -->

- **Shallow binding** — environment of the **call statement that enacts** the passed subprogram. Natural for **dynamic-scoped** languages.
- **Deep binding** — environment of the passed subprogram's **definition**. Natural for **static-scoped** languages.
- **Ad hoc binding** — environment of the **call statement that passed** the subprogram as a parameter.

> 2026 exam twist (ad hoc binding): in `sub A() { call C(B); var value = 10; ... }`, the call that passes B happens **before** A's `var value = 10` is defined, so at that point `value` refers to the **global** `value = 20` → output **20**.

## Overloaded and generic subprograms
**Overloaded subprogram** — same name as another subprogram in the same referencing environment, but a **unique protocol**.

- C++, Java, C#: disambiguated by the **parameter profile**; coercions complicate matching (several candidates may be reachable via coercion).
- Ada: the **return type** can also disambiguate. That can't work in C++/Java/C# because a function call's result can be ignored or used in a mixed-mode expression (the context doesn't fix the expected type).

**Generic (polymorphic) subprograms** take different parameter types in different calls.

- **Ad hoc polymorphism** — via overloaded subprograms.
- **Parametric polymorphism** — a subprogram takes a **generic parameter** describing parameter/return types; each instantiation gets different types.

**C++ templates**

```cpp
template <class T>
T max(T first, T second) { return first > second ? first : second; }
int a, b, c;  c = max(a, b);   // compiler generates an int version
```

Versions are created at **compile time**, one per new type used (when called or when its address is taken with `&`). Works with primitives and classes.

**Java 5.0 generics**

- Generic parameters must be **classes** — no primitives (`int` illegal).
- Instantiated **once**: internally `T` becomes **`Object`** (`public static Object doIt(Object[] list)`); the compiler inserts **casts** so misuse is caught at **compile time**.
- **Bounded types**: `<T extends Comparable>` — T must inherit from/implement `Comparable`.
- **Wildcards**: `Collection<?>` — any object type (can also be bounded with `extends`).

**C# 2005 generics**

- Versions created at **run time**: for primitive types almost like C++ (a version per type); for objects, one version using `Object`.
- **No wildcards**.
- Actual type parameters can be **omitted when the compiler can infer** them: `int myInt = MyClass.DoIt(17);`

> Not examinable: 9.5.3 and 9.10.4.

## Design issues for functions and user-defined operators
- **Side effects** — parameters should ideally be in-mode; pure functional languages enforce this.
- **Number of return values** — usually one. **Ruby** can return several (as an array): `return 1, 2, 3, 4`.
- **Return types** — C/C++: any type **except arrays and functions** (simulate with pointers / function pointers); C++ also user types. Java/C#: any type (but methods aren't types). **Python/Ruby**: any class — and methods are **first-class objects**, so they can be returned.

**User-defined overloaded operators** — C++, Python, Ruby:

```python
def __add__(self, second):
    return Complex(self.real + second.real, self.imag + second.imag)
# x + y  is the same as  x.__add__(y)
```

## Closures (very important)
A **closure** = a subprogram **plus the referencing environment where it was defined**. Needed when a nested subprogram can be called from anywhere — it must still see the non-local variables it was created with.

```javascript
function makeAdder(x) {
  return function(y) { return y + x; }   // anonymous function = closure
}
var add10 = makeAdder(10);
var add5  = makeAdder(5);
add10(20);   // 30
add5(20);    // 25
```

Each call to `makeAdder` creates a new environment; `add10` keeps `x = 10`, `add5` keeps `x = 5`. Since a closure may be called after `makeAdder` returns (when `x` would be out of scope), the captured variables need **unlimited extent** — their lifetime is the whole program.

<!-- diagram:closure -->

**How to trace a closure question**

1. Find the call that **creates** the closure — note the values of its parameters/variables.
2. Substitute them into the returned function.
3. Apply the returned function to the later argument.

```javascript
function doSomething(a, b) {
  return function(val) { if (val < 50) return a; else return b; }
}
var thing = doSomething(5, 2);
thing(10);   // 10 < 50 → returns a → 5
```

## Coroutines
A **coroutine** has **multiple entry points**, which it **controls itself** (it remembers where it stopped). Introduced in **SIMULA 67**, supported in Lua. Also called **symmetric control** — caller and called coroutines are more equal.

- A coroutine call is a **resume**.
- The **first** resume of a coroutine starts at its **beginning**; later resumes continue **just after the last statement executed** (its last `resume`).
- Coroutines can resume each other forever. Execution is **interleaved, not overlapped** — **quasi-concurrent**.

<!-- diagram:coroutine -->

**How to trace a coroutine question**

Keep a "bookmark" for each coroutine (where it will continue). Execute statements one by one; at `resume X` set the current coroutine's bookmark to the next statement and jump to X's bookmark (or X's start if never run). When a coroutine reaches its end, execution stops (unless the question says otherwise).

```
coroutine A { print "First "; resume B; print "Second " }
coroutine B { print "Third "; resume A; print "Fourth " }
main { resume B }
→ Third First Fourth
```

# Brief
**Terms**: definition (interface + actions), header, call, formal vs actual, **profile** (number/order/types), **protocol** (profile + return type), declaration/prototype. Python `def` is executable; Ruby outside-class methods belong to Object.
**Correspondence**: positional vs keyword. Defaults (C++: must be last). Variable parameters: C# `params` (same type), Ruby `*p` / Python (mixed).
**Procedures** modify; **functions** return (ideally no side effects). Locals usually stack-dynamic.

**Passing**: value (in, copy) · result (out, copy back; `sub(p1, p1)` order problem) · value-result (copy both ways) · reference (access path; efficient, aliases, side effects) · name (textual substitution, late binding: `foo(val, arr[val])` → 1 8).
C value (+ pointers); C++ value/reference; **Java all by value**; C# `ref`; **Perl @_ = reference**; Python/Ruby pass-by-assignment.
Type checking params: none (Fortran 77, old C, Perl, JS, PHP), always (Java, Ada), impossible (Python, Ruby — typeless variables).

**Passed subprograms**: shallow (environment of the call that runs it) · **deep** (where it's defined) · ad hoc (call that passed it). Indirect calls: C function pointers, C# (multicast) delegates. Java: no subprogram parameters.
**Overloading**: unique protocol; Ada can use return type. **Generics**: C++ templates (compile-time copies, primitives OK) · Java (classes only, erased to Object + casts, bounds, wildcards `?`) · C# (run-time instances, no wildcards, type inference).
**Functions**: Ruby multiple returns; C/C++ can't return arrays/functions; Python/Ruby methods first-class.
**Closure** = function + defining environment; captured variables have unlimited extent (`makeAdder`).
**Coroutine** = multiple entries, resume continues after last stop; quasi-concurrent; SIMULA 67.

# Traps
- **Protocol** includes the return type; **parameter profile** doesn't.
- Java passes **everything by value** — including object references.
- Perl's `@_` elements are aliases → pass-by-**reference**.
- Pass-by-result transfers by **copy** at return; `sub(p1, p1)` depends on copy-back order.
- Deep binding is natural for **static** scoping; shallow for **dynamic** scoping.
- Ad hoc binding uses the environment of the **call that passed** the subprogram — check what's declared **at that point**.
- Java generics: no primitive type parameters; one run-time instance using `Object`. C# has no wildcards.
- In C++ default parameters must appear **last**.
- Coroutine: first resume starts at the top; later resumes continue **after** the last `resume` executed.
- Closure output: trace the values captured when the closure was **created** — `doSomething(5, 2)` then `thing(10)` → `5`.

# Flashcards
Q: Parameter profile vs protocol?
A: Profile (signature): number, order and types of parameters. Protocol: profile plus return type.

Q: What does it mean that Python subprogram definitions are executable?
A: def runs as a statement; the function exists only after it executes, and different definitions can be chosen at run time (e.g. inside an if).

Q: Why must C++ default parameters come last?
A: Parameters are positional; the compiler couldn't tell which ones were omitted otherwise.

Q: Why must C# params arguments share a type?
A: They're collected into a typed array (params int[] list).

Q: Five parameter-passing implementation models?
A: Pass-by-value, -result, -value-result, -reference, -name.

Q: Problem with pass-by-result and sub(p1, p1)?
A: p1's final value depends on the order in which the formals are copied back.

Q: Disadvantages of pass-by-reference?
A: Slower (indirect) access, unwanted side effects, aliases (fun(total, total)).

Q: Output of foo(val, arr[val]) with a = 1; print(a, b) under pass-by-name (val = 0, arr = {2, 8, 9})?
A: 1 8 — textual substitution makes b mean arr[val] after val becomes 1.

Q: Java's parameter passing?
A: All pass-by-value; object references are passed by value.

Q: Perl's parameter passing?
A: Actuals placed in @_, whose elements are aliases → pass-by-reference.

Q: Shallow, deep and ad hoc binding?
A: Shallow: environment of the call that runs the passed subprogram. Deep: environment of its definition. Ad hoc: environment of the call that passed it.

Q: C++ templates vs Java generics?
A: C++: a new version per type at compile time, primitives allowed. Java: classes only, one version using Object with compiler-inserted casts.

Q: Two C# generics differences from Java?
A: No wildcards; type arguments can be omitted when inferable. (Instances created at run time.)

Q: What is a closure?
A: A subprogram together with the referencing environment where it was defined; captured variables need unlimited extent.

Q: Where does a resumed coroutine continue?
A: First resume: at its beginning. Later resumes: just after the last statement it executed.

Q: Why can't Ada-style return-type overloading work in C++?
A: A call's result can be ignored or used in mixed-mode expressions, so the context doesn't determine the expected return type.
