# Notes

## OOP languages and the three requirements
Kinds of OOP languages: procedural/data-oriented languages with OOP added (C++); functional languages with OOP (CLOS); newer languages that support only OOP but use imperative structures (Java, C#); **pure** OOP languages (Smalltalk, Ruby).

**Abstract data types (ADTs)** — Ch 11 (not directly examinable): a user-defined type whose representation and operations form a **single syntactic unit** and whose representation is **hidden**. On their own ADTs have **no** inheritance, polymorphism or dynamic binding.

An OOP language must support:

1. **Abstract data types** (classes),
2. **Inheritance** — the central theme of OOP,
3. **Polymorphism** — dynamic binding of method calls to methods.

**Why inheritance?** ADTs are hard to reuse without changes, and all ADTs are independent and at the same level. Inheritance lets you **reuse** an ADT with small modifications and organise classes in a **hierarchy**.

## OO vocabulary
| Term | Meaning |
|---|---|
| Class | an ADT |
| Object | a class instance |
| Derived class / subclass | a class that inherits |
| Parent class / superclass | the class inherited from |
| Method | subprogram defining an operation on objects |
| Message | a call to a method (`obj.meth()`: method name + destination object) |
| Message protocol / interface | the entire collection of an object's methods |
| Override | a subclass redefines an inherited method |
| Class variable / instance variable | one per class / one per object |
| Class method / instance method | accepts messages to the class / to objects |

Inheritance can be complicated by **access controls**: hide entities from subclasses; hide from clients; or hide from clients while allowing subclasses to see them (protected).

**Single vs multiple inheritance.** A disadvantage of inheritance for reuse: it creates **interdependencies** among classes, which can complicate maintenance.

## Dynamic binding and abstract classes
A **polymorphic reference** can refer to objects of a class **or any descendant**:

```cpp
Person* p = new Student();
p->print();   // must bind to Student's print → dynamic binding
```

When an **overridden** method is called through a polymorphic variable, binding to the right method must be **dynamic**. This makes systems **easy to extend** during development and maintenance.

- **Abstract method** — no definition, only a protocol.
- **Abstract class** — has at least one abstract method; **cannot be instantiated**.

## Design issues for OO languages
**1. Exclusivity of objects**

| Approach | Advantage | Disadvantage |
|---|---|---|
| Everything is an object | elegance, pure uniformity | simple operations are **slow** |
| Add objects to a complete (imperative) typing system | simple operations fast | confusing type system |
| Imperative types for primitives, objects for everything else (Java) | fast primitives, small type system | two type systems must still mix (wrappers) |

**2. Are subclasses subtypes?** Does an **"is-a"** relationship hold? If so, a subclass object can be used wherever a parent object is expected: the subclass may only **add** variables and methods, and override methods only in **compatible** ways (same number of parameters; type-compatible parameters and return type).

**3. Single and multiple inheritance.** Multiple inheritance (inherit from 2+ classes): ✓ sometimes convenient and valuable. ✗ some **inefficiency** (dynamic binding costs a little more) and **language/implementation complexity**, mostly from **name collisions** — two parents with entities of the same name. The collision is **implicit** in **diamond inheritance**.

<!-- diagram:diamond -->

**4. Allocation and deallocation of objects.** ADT-like objects can live on the **stack** or be created on the heap; if **all** objects are heap-dynamic, access is uniform through references, assignment is a reference copy, and dereferencing can be implicit. With **stack-dynamic** objects and subtypes there's a problem: `A aVar; B bVar; aVar = bVar;` **truncates** (object slicing) the B part. Is heap deallocation explicit or implicit (garbage collection)?

**5. Dynamic and static binding.** Should every message be dynamically bound? None → lose the benefits; all → inefficient. Option: let the programmer choose.

**6. Nested classes.** If a class is only needed by one class, nest it there (or inside a subprogram). Issue: visibility of nesting-class members to the nested class and vice versa.

**7. Initialisation of objects.** Are objects initialised when created (explicitly or implicitly)? How are **parent-class members** initialised when a subclass object is created?

## Smalltalk — the pure OO language
- **Everything is an object**; no imperative features; **all objects are heap-allocated** (slow); all computation is **objects sending messages** (uniform but slow).
- Objects accessed through **typeless reference variables**, implicitly dereferenced; all deallocation is **implicit** (garbage collector).
- **Inheritance:** a subclass inherits all instance variables, instance methods and class methods; **all subclasses are subtypes** (nothing can be removed); a method with the same name and protocol **overrides and hides** the parent's (reach it with **`super`**); **no multiple inheritance**.
- **Dynamic binding of everything:** to find a method, search from the receiving object's class **up the hierarchy to `Object`** — another reason it's slow.

## C++
**General:** evolved from C and SIMULA 67; a **hybrid** language — mixed type system (imperative structs/unions + classes), functions outside classes allowed (procedural + OO); **efficient** (Smalltalk is ~10× slower).

**Inheritance:** a class needn't have a parent. Member access: **public** (subclasses and clients), **private** (class and **friends** only), **protected** (class and subclasses, not clients).

**Derivation access:**

- **public derivation** — inherited public/protected members stay public/protected;
- **private derivation** — inherited public/protected members become **private** → the subclass **is not a subtype**. Useful to reuse an implementation without exposing the parent's interface.

```cpp
class base_class { private: int a; float x;
                   protected: int b; float y;
                   public: int c; float z; };
class subclass_1 : public base_class { ... };   // b, y protected; c, z public
class subclass_2 : private base_class { ... };  // b, y, c, z private
class subclass_3 : private base_class {
  using base_class :: c;                        // re-export c as if inherited publicly
};
```

**Multiple inheritance** is supported; resolve same-named inherited members with the **scope resolution operator**: `Drawing::display()`.

**Message binding — chosen by the programmer at class design time:**

- **Static binding by default** (faster).
- **`virtual`** methods are **dynamically bound** when called through a pointer/reference to a polymorphic object.
- A **pure virtual** function (`virtual void draw() = 0;`) has no definition; a class with one is **abstract**.

```cpp
Shape *ptr_shape = circ;
ptr_shape->draw();   // dynamically bound → Circle::draw
rect->draw();        // statically bound → Rectangle::draw
```

**Stack objects:** assigning a subclass object to a parent-class variable **copies only the parent's members** (truncation) and the call is **statically bound**:

```cpp
Rectangle rect; Square sqr;
rect = sqr;
rect.draw();   // Rectangle's draw
```

## Java
**General:** all data are objects **except primitive types** (with **wrapper classes**); all objects descend from **`Object`**, are **heap-dynamic** (created with `new`) and accessed through **reference variables**; memory reclaimed by a **garbage collector**, which implicitly calls **`finalize`** — but **when** that happens is **unpredictable**.

**Inheritance:** **single inheritance only**. **Interfaces** give some benefits of multiple inheritance — they contain only method **declarations** and **named constants** (simpler than C++ multiple inheritance: no inherited implementations or data to collide). **`final`** methods can't be overridden.

```java
public interface Comparable<T> { public int compareTo(T b); }
```

**Dynamic binding:** **all** messages are dynamically bound, except when overriding is impossible — **`final`**, **`private`** or **`static`** methods → statically bound (dynamic binding would serve no purpose).

**Nested classes**

- The nesting class can access **all** members of a nested class.
- **Inner class** (non-static nested) — can access **all members of its nesting class**.
- **Static nested class** — **cannot** access nesting-class members.
- **Local nested class** — defined in a method; no access specifier; visible only in that method.

## C#
**General:** OOP support similar to Java. Has `class` and **`struct`** — a C# struct is weaker than C++'s: **stack-dynamic**, **no inheritance**, no members referencing the struct itself.

**Inheritance:** C++ syntax for class definitions. To **replace** (hide) an inherited method, mark the new one **`new`**; call the parent's version with **`base.`**: `base.Draw()`. Supports **interfaces** like Java. ✓ explicit marking prevents accidental overriding / documents intent; ✗ more to write.

**Dynamic binding:** the base method must be marked **`virtual`** and the overriding method **`override`** (explicit → readable and reliable; ✗ less writable, and a parent not marked `virtual` can't be overridden). Abstract methods are marked **`abstract`**. All classes derive from **`Object`**.

**Nested classes:** a directly nested class behaves like a Java **static nested class** — it **cannot** access members of the nesting class; there's no equivalent of Java's inner (non-static) classes.

## Ruby
**General:** **everything is an object**; all computation is **message passing**; **class definitions are executable** (a second definition can **add** members); **method definitions are executable** too, so methods can be **changed at run time**; all variables are **typeless object references**.

**Access control:** **all data is private** and that can't be changed; methods can be public, private or protected, and method access is checked **at run time** (errors only found when running). Getters/setters have shortcuts.

**Inheritance:** no true multiple inheritance (modules/mixins instead); access control of a parent's methods can change in the child → **subclasses are not necessarily subtypes**; **no abstract classes**.

**Dynamic binding:** variables are typeless references, so all references are **polymorphic** and binding is dynamic.

# Brief
**OOP = ADTs + inheritance + polymorphism (dynamic binding).** Inheritance → reuse with changes + hierarchies; cost: class interdependence.
Vocabulary: class, object, subclass/superclass, method, message (method name + destination object), message protocol, override, class vs instance variables/methods.
Polymorphic reference → dynamic binding of overridden methods. Abstract method (no body) → abstract class (can't instantiate).

**Design issues**: exclusivity of objects · subclasses as subtypes ("is-a", compatible overrides) · single vs multiple inheritance (name collisions; implicit in diamonds) · stack vs heap objects (truncation) · static vs dynamic binding · nested classes · initialisation.

| | Smalltalk | C++ | Java | C# | Ruby |
|---|---|---|---|---|---|
| Objects | all, heap | stack or heap | heap (+ primitives) | heap classes, stack structs | all |
| Multiple inheritance | no | yes (`::`) | no (interfaces) | no (interfaces) | no (mixins) |
| Dynamic binding | all | only `virtual` | all except final/private/static | `virtual` + `override` | all |
| Subclasses subtypes? | always | not with private derivation | yes | yes | not necessarily |
| Notes | super, GC, slow | public/private/protected + private derivation, re-export | finalize unpredictable, inner vs static nested | `new` hides, `base.`, nested = static | executable classes/methods, data always private, no abstract classes |

# Traps
- Implicit name collision happens in **diamond** inheritance — a method defined in the common ancestor (A) reaches D via both B and C.
- C++ binding is **static by default**; only `virtual` methods called through pointers/references are dynamic.
- Assigning a stack-allocated subclass object to a parent variable in C++ **truncates** it and binds **statically**.
- Private derivation in C++ means the subclass is **not a subtype**.
- Java binds statically only for **final, private and static** methods.
- Java **inner** classes can see nesting-class members; **static nested** classes can't; C# nested classes behave like Java static nested classes.
- C# needs **both** `virtual` (parent) and `override` (child) for dynamic binding; `new` hides instead.
- Ruby: data is **always private**; subclasses aren't necessarily subtypes; no abstract classes.
- Smalltalk is slow because everything is a heap object, every operation is a message, and method lookup climbs the hierarchy.

# Flashcards
Q: Three features an OOP language must support?
A: Abstract data types, inheritance, polymorphism (dynamic binding of messages to methods).

Q: What is a message and its two parts?
A: A call to a method: the method name and the destination object.

Q: What is an abstract class?
A: A class with at least one abstract method (no definition); it cannot be instantiated.

Q: Three approaches to the exclusivity of objects?
A: Everything is an object (elegant, slow); objects added to a full type system (fast, confusing); imperative primitives + objects for the rest (fast, but two type systems).

Q: When is a subclass a subtype?
A: When an is-a relationship holds: it only adds members and overrides compatibly (same number of parameters, compatible types).

Q: Disadvantages of multiple inheritance?
A: Some inefficiency in dynamic binding and language/implementation complexity from name collisions (implicit in diamond inheritance).

Q: C++ public, private, protected members?
A: Public: subclasses and clients. Private: the class and friends. Protected: the class and subclasses, not clients.

Q: Effect of C++ private derivation?
A: Inherited public/protected members become private; the subclass is not a subtype. Members can be re-exported with using base::member.

Q: How does C++ decide static vs dynamic binding?
A: Static by default; virtual methods called through pointers/references are dynamically bound. Pure virtual → abstract class.

Q: When does Java use static binding?
A: For final, private and static methods.

Q: Java inner vs static nested class?
A: Inner (non-static) classes access all nesting-class members; static nested classes cannot.

Q: How does C# mark dynamic binding and hiding?
A: virtual in the parent + override in the child for dynamic binding; new to hide; base.Method() calls the parent version.

Q: C# struct restrictions?
A: Stack-dynamic, no inheritance, no members referencing the struct itself.

Q: Ruby's OOP peculiarities?
A: Executable class/method definitions (can change at run time), all data private, run-time access checks, subclasses not necessarily subtypes, no abstract classes.

Q: Why is Smalltalk slow?
A: All objects on the heap, all computation via messages, and dynamic method lookup searches up the hierarchy.
