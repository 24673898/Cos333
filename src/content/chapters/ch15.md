# Notes

## Why functional languages exist
Imperative languages (C, Java, …) are modelled on the **von Neumann architecture**: variables model memory cells, assignment models moving data between memory and CPU, and iteration is efficient. Their design goal is **efficient execution**; suitability for software development comes second.

Functional languages are modelled on **mathematical functions** instead:

- a solid theoretical basis (lambda calculus),
- closer to the way the *user* thinks about the problem,
- **unconcerned with the machine architecture**.

| | Imperative | Functional |
|---|---|---|
| Execution | Efficient | Inefficient |
| Syntax & semantics | Complex | Simple |
| Concurrency | Designed by the programmer | Can be done automatically |

> In a pure functional language there are **no variables** (as in maths), so there is no state to manage and no ambiguity about what a name refers to.

## Side effects and referential transparency
A **functional side effect** happens when a function changes one of its parameters (two-way parameter) or a global (non-local) variable.

Why it's a problem: if a function used inside an expression changes another operand of that expression, the result depends on **operand evaluation order**.

```c
a = 10;
b = a + fun(&a);   /* if fun changes a, is the left 'a' 10 or the new value? */
```

Two language-design solutions:

1. **Disallow functional side effects** — no two-way parameters, no non-local references in functions. *Advantage:* it works. *Disadvantage:* inflexible (one-way parameters only, no non-local references).
2. **Demand a fixed operand evaluation order** (e.g. Java evaluates left to right). *Disadvantage:* limits some compiler optimisations.

**Referential transparency:** any two expressions that are equivalent (have the same value) can be substituted for one another anywhere in the program **without changing the program's behaviour**.

```c
result1 = (fun(a) + b) / (fun(a) - a);
temp    = fun(a);
result2 = (temp + b) / (temp - a);
```

If `fun` has no side effects, `result1 == result2`. If `fun` changes `a` (or a global), the two differ → referential transparency is **violated**.

- Advantage: program semantics are **much easier to understand** (and to reason about / verify).
- Pure functional programs are referentially transparent because there are **no variables**: no globals to modify, parameters are constants, so functions cannot have **state** — a function's value depends **only on its parameters**.

> Exam pattern: "Which change breaks referential transparency?" → anything that lets a function's result depend on, or change, something other than its parameters (globals, static/history-sensitive locals, input, two-way parameters).

## Scheme basics: atoms, lists and evaluation
Scheme is a **mid-1970s dialect of LISP** (LISP = the first functional language), designed to be **cleaner, more modern and simpler** than other LISP dialects. It uses **static scoping only** and treats **functions as first-class entities**.

**Data objects**

- **Atoms**: symbols (`a`, `x`) and numeric literals (`4.8`, `26`).
- **Lists**: sequences of atoms and/or sub-lists, e.g. `(a b (c d) e)`, stored internally as **singly-linked lists**.

**Data and code look the same.** `(a b c)` can be data (a list of three atoms) or a function application (apply function `a` to `b` and `c`). Consequences: functions are **first-class** — they can be passed as parameters and returned as results — and Scheme programs consist **only of functions** (no operators or control structures in the usual sense: `+` and `if` are functions too).

**How a function application is evaluated**

1. Parameters are evaluated, **in no particular order**.
2. Their values are substituted into the function body.
3. The body is evaluated.
4. The value of the **last expression** evaluated is the function's value.

Literals evaluate to themselves.

## Primitive functions, define and output
**Arithmetic** (all are functions, written prefix): `+ - * / abs sqrt remainder modulo min max`.
`(+ 5 2)` → `7`. Most accept many parameters — `(+ 5 2 8 9)` — **except** `abs`, `sqrt` and `remainder`.

Integer division gives **exact fractions**: `(/ 1 4)` → `1/4`; use a float (`(/ 1.0 4)`) to get `0.25`.

**define** has two forms:

```scheme
(define pi 3.141593)          ; bind a name to a value — only once (not a variable!)
(define two_pi (* 2 pi))
(define (square x) (* x x))   ; bind a name to a function
(square 5)                    ; → 25
```

`define` is special: its first parameter is **not evaluated** (if it were, Scheme would complain the name is undefined).

**Output:** `(display expr)` and `(newline)`. Usually not needed — the interpreter prints every top-level result. Explicit I/O is **not part of pure functional programming**: input changes program state and output is a side effect.

## Predicates and control flow
A **predicate** returns a Boolean: `#t` or `#f` (sometimes `()` is used for false; any non-null list counts as true).

- Numeric: `= > < >= <=` (many parameters) and `even? odd? zero? positive? negative?` (one value).
- `not` inverts a Boolean.
- Lists: `(list? x)` — is it a list? `(null? x)` — is it **completely** empty? `(null? '())` → `#t`, but `(null? '(()))` → `#f`.

**Two-way: `if`** — `(if predicate then_exp else_exp)`

**Multi-way: `cond`** — evaluates to the expression of the **first** predicate that is true; the optional `else` catches everything else. If nothing is true and there's no `else`, the result is unspecified.

```scheme
(cond
  ((null? lis) '())
  ((positive? (car lis)) ...)
  (else ...))
```

**Repetition:** there are no variables, so there are **no loop control variables and no loops**. All repetition is done with **recursion**.

## List functions: quote, list, car, cdr, cons
The interpreter always evaluates parameters — but a list parameter like `(a b c)` would be mistaken for a function call. **`quote`** (abbreviated `'`) returns its parameter **unevaluated**: `'(a b)` ≡ `(quote (a b))`.

| Expression | Result |
|---|---|
| `(list 'a 'b '(c d))` | `(a b (c d))` |
| `(car '(a b c))` | `a` |
| `(car '((a b) c d))` | `(a b)` |
| `(car 'a)`, `(car '())` | **error** |
| `(cdr '(a b c))` | `(b c)` |
| `(cdr '(a))` | `()` |
| `(cdr 'a)`, `(cdr '())` | **error** |
| `(cons 'a '(b c))` | `(a b c)` |
| `(cons '(a b) '(c d))` | `((a b) c d)` |
| `(cons '() '(a b))` | `(() a b)` |
| `(cons 'a '())` | `(a)` |
| `(cons 'a 'b)` | dotted pair `(a . b)` |

`car` = first element, `cdr` = the rest, `cons` = put an element at the **front** of a list. `(car (cdr lis))` = the second element.

## Equality: eqv?, eq? and let
**`eqv?`** — are two values the same? Works for symbols and numbers:
`(eqv? 'a 'a)` → `#t`, `(eqv? 3.4 (+ 3 0.4))` → `#t`, but `(eqv? 3.0 3)` → `#f` (float ≠ integer; use `=` for numeric equality: `(= 3.0 3)` → `#t`). **Does not work for lists:** `(eqv? '(a b) '(a b))` → `#f`.

**`eq?`** — are they the **same object in memory** (pointer comparison)? Reliable for symbols, **unreliable** for lists and numbers. In most cases `eqv?` is more appropriate.

**`let`** binds names to values for use in a body:

```scheme
(define (computation a b c d)
  (let ((top (+ a b))
        (bottom (- c d)))
    (/ top bottom)))
```

Semantics: evaluate all binding expressions, bind the names, then evaluate the body; `let` yields the value of the **last** expression in its body (several expressions are evaluated in sequence). In tests only plain `let` is allowed — **not** `let*` or named `let`, so one binding cannot use another binding from the same `let`.

## The four slide functions (exam benchmark)
Implementation questions are "no more complex than" these. Know them by heart.

```scheme
(define (member atm lis)            ; is atm in the simple list?
  (cond
    ((null? lis) #f)
    ((eqv? atm (car lis)) #t)
    (else (member atm (cdr lis)))))

(define (equalsimp lis1 lis2)       ; are two simple lists equal?
  (cond
    ((null? lis1) (null? lis2))
    ((null? lis2) #f)
    ((eqv? (car lis1) (car lis2)) (equalsimp (cdr lis1) (cdr lis2)))
    (else #f)))

(define (equal lis1 lis2)           ; general lists (atoms or nested lists)
  (cond
    ((not (list? lis1)) (eqv? lis1 lis2))
    ((not (list? lis2)) #f)
    ((null? lis1) (null? lis2))
    ((null? lis2) #f)
    ((equal (car lis1) (car lis2)) (equal (cdr lis1) (cdr lis2)))
    (else #f)))

(define (append lis1 lis2)          ; elements of lis1 followed by lis2
  (cond
    ((null? lis1) lis2)
    (else (cons (car lis1) (append (cdr lis1) lis2)))))
```

**Why can't `list` append?** `(list '(a b) '(c d))` → `((a b) (c d))` — a two-element list of lists. **Why not `cons` lis2's elements onto lis1?** `cons` only adds to the **front**. So `append` conses lis1's elements onto lis2 *in reverse order* via recursion:

```
(append '(a b) '(c d)) → (cons a (append '(b) '(c d)))
                       → (cons a (cons b (append '() '(c d))))
                       → (cons a (cons b '(c d)))  →  (a b c d)
```

## Tail recursion
Recursive functions are normally **slower** and use **more memory** than iteration (each call waits on the stack).

A function is **tail recursive** if the recursive call is the **last operation** in the function. Then the interpreter can **automatically convert it to iteration**, making it much faster and memory-efficient. The **Scheme language definition requires** all tail-recursive functions to be converted to iteration.

```scheme
(define (factorial n)                 ; NOT tail recursive: * happens after the call
  (if (<= n 1) 1 (* n (factorial (- n 1)))))

(define (facthelper n partial)        ; tail recursive: the call is the last thing
  (if (<= n 1)
      partial
      (facthelper (- n 1) (* n partial))))
(define (factorial n) (facthelper n 1))
```

The trick: carry the partial result in an extra **accumulator** parameter.

## Functional forms: mapcar and eval
A **functional form** (higher-order function) takes functions as parameters and/or yields a function.

**Apply-to-all** — apply a function to every element, building a new list:

```scheme
(define (mapcar fun lis)
  (cond
    ((null? lis) '())
    (else (cons (fun (car lis)) (mapcar fun (cdr lis))))))

(mapcar square '(3 4 2))   ; → (9 16 4)
```

**Functions that build code:** because code is a list and the interpreter is available as the function **`eval`**, a Scheme function can build Scheme code and run it:

```scheme
(define (adder lis)
  (cond
    ((null? lis) 0)
    (else (eval (cons '+ lis)))))   ; builds (+ 3 4 5) then evaluates it

(adder '(3 4 5))   ; → 12
```

The `+` must be **quoted** so it is inserted as a symbol rather than evaluated.

# Brief
**Functional vs imperative.** Imperative = von Neumann, efficient execution, complex. Functional = maths functions, simple syntax/semantics, inefficient, easy automatic concurrency, no variables.

**Side effect** = function changes a parameter or global. Fixes: ban them (inflexible) or fix evaluation order (hurts optimisation).
**Referential transparency** = equal expressions are interchangeable without changing behaviour. Pure FP has it because there's no state.

**Scheme** = clean, simple LISP dialect (mid-70s), static scope, first-class functions. Atoms + lists; code and data share the list form. Parameters evaluated in no particular order; value = last expression.

**Key functions**

- `quote`/`'` stops evaluation. `list` builds a list from its parameters.
- `car` first, `cdr` rest (both error on `()` and atoms), `cons` adds to the front (`(cons 'a 'b)` = dotted pair).
- `eqv?` value equality (not lists, `3.0 ≠ 3`); `eq?` pointer equality (unreliable for numbers/lists).
- `null?` only true for `()`. `cond` → first true clause. `let` → bind, then body.
- Repetition = recursion only.

**Tail recursion** = recursive call is the last operation → Scheme *must* turn it into iteration. Use an accumulator.

**Functional form** = takes/returns functions (`mapcar`). **eval** runs code you built (`(eval (cons '+ lis))`).

**Implementation recipe:** base case `(null? lis)` → recurse on `(cdr lis)` → `cons` (keep/transform), skip (omit), `+ 1` (count), `+ x` (sum). For pairs, also check `(null? (cdr lis))`.

# Traps
- `(car '())` and `(cdr '())` are **errors**, not `()`. A compare-neighbours function needs a `(null? (cdr lis))` base case.
- `(eqv? 3.0 3)` is `#f` but `(= 3.0 3)` is `#t`; `(eqv? '(a b) '(a b))` is `#f`.
- `(null? '(()))` is `#f` — the list contains one element (the empty list).
- `define` binds a name **once**; it is not assignment.
- Tail recursion: `(* n (factorial (- n 1)))` is NOT tail recursive — the multiplication happens after the call returns.
- `let*` and named `let` are **banned** in implementations; plain `let` bindings can't see each other.
- Function call syntax is `(f x)`, never `f(x)`; operators are prefix `(= x 0)`, never `(x = 0)`.
- `(/ 22 7)` is an exact fraction; questions saying "22/7 is a fraction literal, not a division" want you to write `(/ 22 7)`.
- Parameters of a function application are evaluated in **no particular order**.

# Flashcards
Q: What is referential transparency?
A: Any two equivalent expressions can be substituted for one another without changing the program's behaviour. Pure functional languages have it because they have no variables/state.

Q: Two language-design solutions to functional side effects (with drawbacks)?
A: 1) Disallow them (no two-way params, no non-local refs) — inflexible. 2) Fix operand evaluation order (e.g. Java left-to-right) — limits compiler optimisations.

Q: What does (cons 'a 'b) yield?
A: The dotted pair (a . b) — the second parameter isn't a list.

Q: (cdr '(a)) vs (cdr '())?
A: (cdr '(a)) → (). (cdr '()) → error.

Q: eqv? vs eq?
A: eqv? compares values (symbols & numbers, not lists). eq? compares memory addresses — unreliable for numbers and lists. Prefer eqv?.

Q: What makes a function tail recursive, and why does it matter in Scheme?
A: The recursive call is the last operation. The Scheme definition requires such functions to be converted to iteration — faster and less memory.

Q: What is a functional form? Give the slide example.
A: A function that takes functions as parameters and/or returns a function. mapcar (apply-to-all): (mapcar fun lis).

Q: How can a Scheme function build and run code?
A: Build a list (e.g. (cons '+ lis)) and pass it to eval, the interpreter available as a function.

Q: Why is quote needed?
A: The interpreter evaluates all parameters; lists look like function applications, so quote returns its parameter unevaluated.

Q: How is repetition done in Scheme?
A: Only with recursion — no variables means no loop control variables or loops.

Q: Order of parameter evaluation in a Scheme function application?
A: No particular order. Then values are substituted into the body and the last expression's value is returned.

Q: Why can't you append two lists with the list function?
A: (list '(a b) '(c d)) gives ((a b) (c d)) — a list of two lists, not one combined list.

Q: Functional vs imperative: execution, syntax, concurrency?
A: Imperative: efficient, complex, programmer-designed concurrency. Functional: inefficient, simple, can be made concurrent automatically.

Q: Is (null? '(())) true?
A: No — #f. The list contains one element (the empty list).
